# 未来演进：从本地 Relay 到异构节点协同

## 1. 演进原则

本地 MVP 的目标是验证协同协议和人工控制，而不是抢先绑定某个厂商、渠道或网络架构。后续扩展应遵循四条原则：

1. **参与方自主。** 每个角色保留自己的通用 Agent、资料和工作习惯。
2. **协议中立。** Relay 处理的是结构化事项消息，不依赖具体模型、聊天产品或 IDE。
3. **最小共享。** 跨节点默认只共享任务、结论、证据引用和获授权附件，不默认同步个人资料库或完整对话。
4. **人承担责任。** 自动化不能绕过正式审批、签发、停工、复工或对外承诺的人工权限。

## 2. Adapter 的演进方向

| Adapter 类型 | 未来作用 | MVP 中的对应物 |
| --- | --- | --- |
| Codex CLI Adapter | 在授权的本地环境启动结构化任务，回传结果 | Mock 专业 Agent |
| Hermes 或其他 Agent Adapter | 将其他本地/远端 Agent 的结果映射为统一消息 | Mock 专业 Agent |
| Human/File Adapter | 由人上传文件、补充说明或确认结果 | Human Adapter |
| 邮件 Adapter | 将邮件正文和受控附件转换为事项输入或回复草稿 | Ingress/Egress Mock |
| 企业 IM Adapter | 通过授权的企业应用接收事件、发送待确认草稿 | Ingress/Egress Mock |
| 项目系统 Adapter | 对接已授权的台账、文档或审批系统 | 证据引用字段 |

这些方向不假定任何特定产品必然开放接口。每个 Adapter 都应以明确授权、可审计、可撤销为前提。

## 3. 多节点 Gateway 模式

本地 MVP 只有一个 Relay 进程。未来可以让每个组织或节点运行自己的 Gateway：

```text
专业人员本地资料 / Agent
-> 本地 Gateway
-> 经授权的协同消息
-> 项目 Relay 或对方 Gateway
-> 对方角色的本地 Agent / 人工
```

这样做的目的不是把所有资料汇入一个中心，而是允许各节点只对外发布经过确认的协作结果。

未来的技术形态可以包含安全的 HTTP JSON、WebSocket 或受控文件收件箱；这些只是传输方式，不能替代消息契约中的 `trace_id`、角色、轮次、证据和人工审批字段。

## 4. 隐私与数据边界

协同协议应区分四类信息：

| 类别 | 示例 | 默认处理 |
| --- | --- | --- |
| 个人/专业私有上下文 | 本地工作笔记、历史资料、个人 Agent 记忆 | 不出本地节点 |
| 项目共享事实 | 已确认的事项、时间、地点、责任角色 | 可按权限进入 Relay |
| 证据引用 | 受控附件标识、版本、摘要、哈希或来源说明 | 默认共享引用，不默认共享原件 |
| 正式对外结论 | 报告、通知、签发文件 | 必须经人工确认后才可生成或发送 |

未来需要补充节点身份、消息签名、权限策略、附件访问控制、审计保留期限和撤销机制。它们是生产化议题，不应在黑客松现场用假设替代。

## 5. 逐步扩展路线

```text
阶段 1：本地 Mock Relay
  验证消息契约、轮次、状态、证据和人工控制。

阶段 2：一个真实本地 Agent Adapter
  在授权环境中接入一个 CLI 或本地 Agent，其他节点仍可为 Mock。

阶段 3：人工/文件入口
  支持受控上传、文件收件箱或邮件导入，保留人工确认。

阶段 4：多个组织 Gateway
  不同角色节点通过安全传输交换最小化消息。

阶段 5：受授权的企业系统 Adapter
  在组织批准、权限清晰的前提下接入企业 IM、台账和归档系统。
```

每一步都必须保持一个原则：协议和审计链比渠道连接数量更重要。
