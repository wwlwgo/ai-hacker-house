# 前端与产品协作任务书

## 1. 这位伙伴要解决什么

本项目不缺“又一个聊天框”，缺的是让观众一眼理解多 Agent 协同发生了什么的可视化。前端/产品伙伴的核心任务是把 Relay 的内部结构变成可操作、可讲解的协同指挥台。

目标观众是黑客松评委、现场 Builder 和第一次看到工程协同的人。页面的单一工作是：让人看懂一个事项从进入、派发、取证、人工纠偏到报告草稿的全过程。

## 2. 明天的前端交付优先级

### P0：必须完成

一个本地浏览器页面，能够加载预置案例并展示：

```text
事项状态
角色状态
消息时间线
证据与结论
Human Adapter 操作
已批准后的报告草稿
```

至少支持“SC 管专项核查”案例的逐步推进。若 Relay Core 尚未接好，允许先由前端使用预置 JSON 模拟事件，但字段名必须与 [MVP 技术设计](MVP-技术设计.md) 的消息契约保持一致。

### P1：有余力完成

- 案例选择器：在“专项核查”和“安全日报”之间切换。
- 证据详情抽屉：点击后展示证据说明、来源角色和关联消息。
- 人工纠偏输入区：插入一条 `human.correction` 后，突出受影响的旧结论与下一轮澄清。
- 可回放时间线：从 `NEW` 一步步推进到 `REPORT_DRAFTED`。

### P2：仅在主链路稳定后

- 展示不同 Adapter 的标识：Mock、Human、未来远端节点。
- 过滤：只看某角色、某轮次、某类消息。
- Markdown 报告预览的排版优化。
- 移动端适配、动效和导出按钮。

## 3. 推荐页面结构

```text
┌──────────────────────────────────────────────────────────────┐
│ 工程协同 Agent Relay                     [案例选择] [Mock]   │
│ 现场管材专项核查 · trace: sc-pipe-001 · 第 2 轮 / 待确认      │
├─────────────┬───────────────────────────┬────────────────────┤
│ 角色轨道    │ 事项轨迹                  │ 证据与结论         │
│             │                           │                    │
│ 业主        │ [R0] 事项创建             │ 建议结论           │
│ 综合监控    │ [R1] 并行核查             │ 事实与冲突         │
│ 通信        │ [H]  人工纠偏             │ 证据引用           │
│ 总监        │ [R2] 定向澄清             │                    │
│             │ [H]  待总监确认           │                    │
├─────────────┴───────────────────────────┴────────────────────┤
│ Human Adapter: [运行下一轮] [补充/纠偏] [暂停] [批准并生成]  │
├──────────────────────────────────────────────────────────────┤
│ 报告草稿 / 审计回放                                            │
└──────────────────────────────────────────────────────────────┘
```

不要把“角色轨道”做成无序群聊列表。它应该像工程事项的流程轨道：每个角色只有与当前事项相关的状态，消息时间线才是叙事中心。

## 4. 关键交互细节

| 交互 | 页面行为 | 对 Relay 的含义 |
| --- | --- | --- |
| 运行下一轮 | 时间线新增一组事件，状态推进 | 受控轮次，不是自动无限聊天 |
| 选择证据 | 右栏切换到证据详情 | 每个结论可回到来源 |
| 人工纠偏 | 弹出简短输入或预设动作，旧前提变为待核 | 人可在中间进入协作链 |
| 暂停事项 | 顶部状态变为暂停，下一轮按钮失效 | 高风险或不确定事项不应继续自动推进 |
| 批准并生成 | 只有总监角色可触发，展示报告草稿 | 人工责任边界 |
| 切换案例 | 保持同一页面结构，替换 `trace_id` 和事件 | 同一 Relay 可支持不同工作流 |

## 5. 视觉方向

不要做赛博、聊天机器人或通用 SaaS Dashboard。建议把它设计成“工程审阅台”：像一张干净、可靠的现场事项记录，而不是营销页。

建议的基础 token：

| 用途 | 色值 | 含义 |
| --- | --- | --- |
| 图纸白 | `#F6F5F0` | 页面底色，像整理后的工程资料 |
| 墨黑 | `#20241F` | 主文字和结构线 |
| 深松绿 | `#236352` | 已核查、已确认、正常轨道 |
| 警示橙 | `#C65D20` | 缺失证据、待处理、需澄清 |
| 证据蓝绿 | `#237C82` | 证据引用和可查看的材料 |
| 灰绿 | `#DDE4DE` | 次级信息、分隔区 |

字体优先保证中文可读和信息密度。使用系统中文无衬线字体，数字、轮次和 `trace_id` 用等宽字体。圆角保持克制，卡片只用于单条消息或单项证据，不给整页套大卡片。

**页面的标志性元素**：把 `trace_id` 对应的消息画成一条“事项轨迹线”。普通消息是细线节点，人工纠偏是明显的折返点，批准节点是终点印记。它直接把“可追溯”变成视觉语言。

## 6. 和后端的接口约定

前端不应直接依赖某个 Agent 或某个大模型。它只消费结构化数据：

```text
case: trace_id, title, status, round
message: sender, receiver, event_type, payload, evidence_refs, timestamp
evidence: id, title, source_role, summary, status
decision: proposed_conclusion, conflicts, human_approval_required
```

先支持静态 JSON，再由后端替换成 SQLite 或 Relay 查询结果。这样两个人可以并行开发。

## 7. 验收标准

- 观众不看代码，也能说出当前事项处在哪个阶段。
- 观众能看到至少两条专业分支和一条人工纠偏。
- 任意一条建议结论都能看到至少一条证据引用。
- “批准并生成报告”在批准前不可用或明确标为待确认。
- 3 分钟演示期间无需滚动长篇模型文本。
- 页面无法完成时，仍能由 CLI/Markdown 时间线支撑 Demo。

## 8. 六小时协作建议

| 时间 | 前端/产品伙伴 | 后端/Agent 伙伴 | 领域负责人 |
| --- | --- | --- | --- |
| 0-30 分钟 | 对齐页面线框与数据字段 | 对齐消息模型和状态机 | 确认案例、角色、人工边界 |
| 30-120 分钟 | 完成静态布局与时间线 | 完成 Mock 事件序列 | 验收文案、证据和场景真实性 |
| 120-210 分钟 | 接入真实状态与人工操作 | 跑通 Relay 主链路 | 注入人工纠偏、检查结论 |
| 210-270 分钟 | 完成证据详情与报告预览 | 审计、回放、异常状态 | 准备路演与 Q&A |
| 270 分钟后 | 视觉打磨与截图 | 修复主链路 | 演练三分钟 Demo |

## 9. 首次沟通时可直接发给前端伙伴的话

我不希望做一个新的聊天机器人，而是想做一个工程事项的协同指挥台：不同角色的 Agent/人工节点围绕同一件事提交任务、证据和结论，人可以随时纠偏，最后由总监确认。后端会提供结构化事件；你可以先用 JSON 做页面。最重要的是把“并行核查、人工折返、证据回溯、批准生成报告”这四件事做得一眼能看懂。
