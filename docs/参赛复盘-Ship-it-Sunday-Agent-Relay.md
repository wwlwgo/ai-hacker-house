## 三、完成内容

### 项目：工程协同 Agent Relay

**要解决的问题**：工程项目中的核心事实散落在不同群组、邮件、表格中。每个角色都能用通用 Agent 写日报、审查文件，但同一件事仍要被反复转发、重新整理。信息跨专业、跨单位流转时，容易丢失来源、证据和责任状态。

**方案**：建立一层中立的协同机制——参与方继续用各自熟悉的工具处理本地资料；需要协作时，将任务、证据和结论转换成统一消息，由 Relay 进行路由、轮次控制、追溯和人工确认。完整时间线用于审计，受控路由用于协作；高风险结论和正式对外交付始终由人确认。

**演示场景**：脱敏的"SC 管壁厚专项核查"——业主提出质疑 → Relay 并行派发给两个专业角色 → 专业 Agent 提交证据 → 人工中途纠偏 → 定向澄清 → 证据汇聚 → 总监确认 → 生成报告草稿。

### 交付物清单

| 类别 | 内容 |
|:--|:--|
| 核心代码 | `src/relay/`（状态机、消息契约、Mock 节点）、`src/reporting/`（报告草稿、LLM 降级）、`streamlit_app.py`（演示 UI） |
| 测试 | 10 个单元测试，全部通过（含状态机约束、错误路径、LLM 降级回退） |
| 演示数据 | 2 个脱敏案例 fixture（SC 管壁厚核查、安全日报） |
| 文档 | README、技术设计、演示脚本、3 分钟路演稿、组队说明、前端协作任务书、未来演进等 12 篇 |
| PPT | 演示用 PPT（核心论点：完整时间线用于审计，受控路由用于协作） |
| Web 入口 | Streamlit 主入口 + 零依赖静态 HTML 降级入口 |

### 技术边界（如实说明）

- MVP 为本地单机运行，使用 Mock 节点和脱敏 fixtures
- 未接入真实微信群、企业 IM、外部 Agent 或项目资料
- LLM 仅用于总监批准后的报告起草增强，默认 Mock 回退；未配置 API Key 也能跑通全流程
- 这是协同协议与运行时的参考实现，不是正式项目管理系统，不替代监理、专业人员或总监的签发责任

### 现场群像：一间屋子里的 AI 样本切片

黑客松除了交作品，也是一次高密度的“人类网络扫描”。现场大多数人明显比我年轻，年龄结构大致可以概括为：年轻人居多，70 后极少。下面是几段让我印象很深的交流，按人物脱离姓名后的“群像”记录。

1. **棕发的 USC 大二学生，已经在做 Agent 创业**

   他在美国 USC 读计算机与设计，暑假回国参加活动，已经和创业伙伴在尝试 AI Agent 方向的创业。他介绍的项目很有意思：不是先规定 Agent 公司“只能做什么”，而是让多个 Agent 自己寻找商机、拆解任务和尝试执行。其中一个 Agent 项目从网站上发现医药学相关的信息需求，写出一本英文小书并实际卖出两本。账还没有算平，但已经有了真实收入；整个项目据说只做了两天。他们每周 Token 开支约 100 美元。对我而言，“卖出两本”比“生成了一堆漂亮 Demo”更有冲击力：它至少说明 Agent 已经开始碰到真实世界的交易闭环。

2. **卷发、英文流利的社区产品创业者**

   这位小伙伴主要做社区类产品，对获客、销售和推广的理解很实战。工程管理的人很容易从“需求、流程、交付”出发思考产品；和他聊天后再次意识到，产品能不能被找到、被理解、被愿意付费，同样是一门硬技术。AI 产品不只是在模型和界面里完成，也是在用户、渠道和运营里完成。

3. **主办方孵化器现场负责人：企业 AI 落地的另一条线**

   对方来自主办方相关孵化器团队，主要关注 AI 项目在大型企业中的落地。听完我的工程监理背景后，他在间歇专门找我聊了很久。他们手上有不少做 AI 产品的团队资源，也希望通过我了解杭州轨道交通及其他行业大企业的真实需求和沟通机会。对方的判断让我印象很深：纯 AI 背景的人不一定能独立完成企业落地，行业场景、组织语言和业务信任同样重要。这与我做 Agent Relay 的出发点并不矛盾，反而互相印证。

4. **已落户 园区 的独立创业者：把机器人当作社会变量来谈**

   他在园区内已落户项目，主要做面向海外的付费产品。除了产品，他聊得更多的是就业、AI 对社会结构的冲击，以及人形机器人在未来 3 至 8 年可能规模化普及后对劳动力市场的影响。未必每一个时间判断都会实现，但我惊讶于他在这个年龄对社会、经济和技术之间关系的思考深度。黑客松里常见的是“怎么把功能做出来”，而他在问“做出来以后，世界会变成什么样”。

5. **正在转型的 AI 从业者：职业选择不应只看标签**

   一位在公司从事 AI 工作的小伙子向我咨询职业转型和招聘机会。我所在企业没有直接岗位，但我把工程行业里跨专业、跨业务的 AI 需求讲给他听：未来很多岗位未必只认原来的行业标签，更看重是否能理解新工具、进入真实业务并形成价值。与其只把自己限定在“做 AI 的人”，不如尝试成为“懂一个行业、也能把 AI 用进去的人”。他后来很认真地表示感谢，这段交流也提醒我：AI 时代的职业路径，可能比过去更像一张网，而不是一条直线。

6. **刚入职蔚来汽车的应届生：用竞赛和实验室打开工作机会**

   他今年本科毕业、刚入职蔚来汽车，负责用 AI 辅助芯片和集成电路质量检测，也参加过多次类似活动。他讲到一个很朴素但有力的经验：大四后没有把主要精力放在常规听课上，而是进入实验室帮老师做事、参加网络和 IT 相关的高水平竞赛；竞赛经历带来实习机会，实习又带来工作机会。他说同学中不少人仍在为就业发愁，而他已经在真实岗位上解决问题。工作之外，他每月还自费花 100 美元以上使用 GPT 产品。这个路径未必适合所有人，但“尽早进入真实问题，而不是只停留在课堂”这件事，值得记下来。

7. **来学习 AI 的投资从业者父亲**

   下午还遇到一位可能从事投资的前辈。他自己并不经常 Vibe Coding，但孩子刚上大一，他已经开始学习 AI，也在带着孩子一起学。因为当时正处在提交作品的关键时间，我没有和他展开太久；但这个画面很有意思：AI Hacker House 里既有刚从学校出来的年轻人，也有已经在替下一代观察技术变化的父亲以及投资者。

整场活动给我的总体感受是：这里的年轻人并不只是“会用几个 AI 工具”，而是在用不同方式提前进入未来。有的人在试商业化，有的人在试企业落地，有的人在试职业路径，有的人已经在试着理解 AI 将怎样重塑社会。作为一个 70 后，我原本以为自己是来交一个项目；到最后更像是来参加一次跨代际的技术交流。能和他们讨论 Agent、Token、产品、就业和行业落地，确实让人感觉自己也年轻了一点。

## 五、结果与遗憾

- 项目完成并提交至公有仓库，演示 UI 可运行、测试全部通过
- Demo 展示环节：由于同时准备了 PPT、日常工作微信截图和 Web UI 三部分材料，3 分钟路演时间不足，Web UI 介绍环节未能完整讲完，略显仓促
- 这是第一次参赛，路演节奏与材料组织缺乏经验，属可改进项

### 路演环节的反思（赛后才意识到）

赛前只被告知"3 分钟路演"，PPT 也是按 3 分钟准备的。但实际操作中，3 分钟需要同时完成：开场介绍、项目由来（结合日常工作场景）、项目界面演示、技术方案说明——这些内容叠加后，3 分钟远远不够，最终导致 Web UI 演示环节仓促收尾。

更深一层的反思：**路演的组织本身，同样可以交给 AI 完成。** 我在赛前把 AI 用在了"开发"环节（代码生成、文档撰写），却没有想到把 AI 用在"表达"环节——用 AI 设计路演结构、拆分 3 分钟的时间分配、生成开场词、规划演示节奏。如果赛前预留 30-40 分钟，把路演安排、开场词和演示流程交给 AI 来设计与演练，效果会好很多。

**这暴露了一个认知盲区：AI 的能力范围是"从构思到交付的全链路"，而我只在其中的"开发"环节使用了它。表达、组织、演示这些环节，同样在 AI 的覆盖范围内，只是我没有想到去用。**

## 六、客观自评

**关于项目本身**：这是一个参考实现级别的 MVP。核心价值是"工程协同的消息契约、受控路由与人在环上的责任边界"这个设计思路，而非技术深度。它不接入真实系统、不使用真实多 Agent 网络、LLM 参与有限——这些是明确的边界，不是隐藏的缺陷。

**关于参赛者**：工程监理行业从业者参加 AI 黑客松并完成从构思、设计、开发、测试、文档到演示的完整闭环，在本行业并不常见。计算机专业背景与 25 年工程管理经验的组合，使得"行业场景理解"与"AI 工具实践"可以互相印证。

**这次参赛想说明的**：不试图证明具备系统开发的技术能力，而是展示：一个长期从事工程管理的人，在 AI 时代依然具备持续学习和独立探索的能力；同时，25 年行业经验积累的场景理解，是 AI 落地（尤其 FDE 方向）中难以被替代的部分。
