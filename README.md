# 工程协同 Agent Relay

> 让不同角色、不同 Agent、不同渠道围绕同一工程事项交换任务、证据和结论，并始终保留人的判断与责任边界。

## 要解决的问题

工程项目中的核心事实往往散落在不同群组、邮件、表格和个人资料中。每个角色都能借助通用 Agent 写日报、审查文件或生成汇报，但同一件事仍要被反复转发、重新整理、逐级确认。信息一旦跨专业或跨单位流转，就容易丢失来源、证据和责任状态。

工程协同 Agent Relay 关注的不是再做一个聊天机器人，而是建立一层中立的协同机制：参与方继续使用自己熟悉的 Codex、TRAE、Hermes 或人工方式处理本地资料；需要协作时，将任务、证据和结论转换成统一消息，由 Relay 进行路由、轮次控制、追溯和人工确认。

## 明天的 MVP

主场景是一个脱敏的“SC 管壁厚专项核查”。业主提出质疑后，Relay 将核查任务并行派发给两个专业角色；专业 Agent 分别提交测量和标准依据；专业人员可在中途纠正对象或标准的误判；Relay 汇聚证据后形成建议结论，最终由总监 Human Adapter 确认并生成报告草稿。

```text
业主质疑
  -> 并行专业核查
  -> 人工纠偏与定向澄清
  -> 证据汇聚
  -> 总监确认
  -> 专项汇报草稿
```

MVP 只在本地单机运行，使用 Mock 节点和脱敏 fixtures。它不接入真实微信群、企业 IM、外部 Agent 或项目资料。可选的 DeepSeek Report Agent 只会在总监批准后读取“已批准结论包”起草 Markdown 报告；它不参与 Relay 的路由、轮次、证据收集或批准决策。

## 为什么是 Agent Relay

- 单 Agent 主要提升个人效率；Relay 解决跨角色协同中的信息重复整理。
- Relay 不要求所有人使用同一种模型、同一种产品或同一个网络节点。
- 每条消息都有 `trace_id`、角色、轮次、证据引用和状态。
- Agent 可以推进任务，人可以随时补充、纠正、暂停、退回或批准。
- 高风险结论和正式对外交付始终由人确认。

## 本地启动

当前 MVP 有两个等价的最小启动入口。优先使用 Streamlit：

```bash
.venv/bin/python -m streamlit run streamlit_app.py
```

也可以直接双击打开零依赖的 [web/index.html](web/index.html)，或在项目根目录运行：

```bash
python3 -m http.server 8000 --directory web
```

然后访问 `http://127.0.0.1:8000`。

Streamlit 已在项目虚拟环境中安装并通过导入验证（1.50.0）。静态 HTML 仍保留为断网或依赖异常时的降级入口。

若希望启用批准后的真实报告起草，在项目根目录创建本地 `.env` 并配置 `DEEPSEEK_API_KEY`；该文件已被 Git 忽略。未配置、网络失败或模型返回异常时，页面会明确标记 `Mock 回退`，并继续生成可演示的确定性草稿。

## 现场实施顺序

1. 向队友分享 [组队说明](docs/组队说明.md)，先确认谁负责 Relay/状态机、谁负责观察面板。
2. 以 [MVP 技术设计](docs/MVP-技术设计.md) 的消息契约和状态机作为实现约束；主链完成、完成一次演练后，才按 [场景矩阵](docs/场景矩阵与扩展路线.md) 接入第二场景。
3. 先按 [脱敏案例](demo-fixtures/sc-pipe-inspection/README.md) 实现并跑通全链路，再补充当前静态观察面板。
4. 若网络或模型不可用，报告节点自动回退为确定性 Mock 草稿；消息链和人工控制不受影响。

## 当前边界

这是一个协同协议与运行时的参考实现，不是正式项目管理系统，也不替代监理、专业人员、总监或任何签发责任。真实 LLM 仅用于批准后的报告起草增强，不能自动签发、盖章或发送。
