# 脱敏案例：专项管材壁厚核查

## 1. 用途与边界

本目录只包含黑客松 Demo 的虚构、脱敏材料，用于验证工程协同 Agent Relay 的消息协议。它不对应任何真实项目、人员、单位、群组、文件编号或现场照片。

`SC` 只是演示标签；目录中的数值、技术要求和结论均为虚构示例，不能作为任何真实工程的规范依据。

场景保留真实工程协作的结构特征：对象存在歧义、多专业并行核查、专业间受控核对、证据来源不同、人工中途纠偏与裁决、结论需经负责人确认。

## 2. 故事线

一位发起方对现场照片中的管材壁厚提出质疑，要求项目团队核查对象类型、实测情况和适用要求。

Relay 创建 `sc-pipe-001`，将任务并行发给两个专业节点：

```text
综合监控专业：核对现场测量记录与该专业依据。
通信专业：核对专业台账与对应的技术要求。
```

第一轮后，通信专业对“测量记录能否直接对应照片对象”提出质疑。Human Adapter 要求对象识别、测量样本关系和依据适用范围分别补齐，第一轮判断不能直接进入结论。第二轮中，综合监控专业经 Relay 向通信专业发起受控交叉核对；通信专业明确台账的可用范围，避免将其扩展为对象关联证据。补充对象识别和专业依据后，总监对每一项结论作出采纳、排除或待补充的裁决，再批准报告结论包。

第一轮的所有专业回复均为“初步核查结果”，不能直接进入报告，也不能跳过对象确认和负责人批准。

## 3. 角色上下文边界

| 角色 | 可见的模拟上下文 | 不可见内容 |
| --- | --- | --- |
| 综合监控 Agent | 模拟测量记录、模拟专业条款摘要 | 通信专业原始台账 |
| 通信 Agent | 模拟抽检台账、模拟专业条款摘要 | 综合监控测量细节 |
| 汇总 Agent | 两个专业节点返回的结构化结果 | 各节点未提交的私有资料 |
| 总监 Human Adapter | 完整审计链、建议结论 | 不自动生成或修改专业证据 |
| 报告 Agent | 已批准的结论包 | 未确认的早期聊天或被否定前提 |

## 5. 预期消息序列

`case.json` 中的 `next_iteration_design.message_storyboard` 定义当前 Relay 的十条脱敏消息，也是后续页面升级的唯一故事线来源。旧字段仅为当前页面控制入口和历史测试兼容保留。

```text
1. 发起方创建事项，总监收紧核查边界。
2. 两个专业提交彼此独立的初步判断。
3. 通信专业提出质疑：已有材料不能证明照片对象与测量样本直接对应。
4. 总监 Human Adapter 纠偏，暂停直接下结论。
5. 综合监控经 Relay 向通信专业发起受控交叉核对，通信专业回复其台账的适用边界。
6. 综合监控补充对象识别、测量和依据的可追溯关系。
7. 总监将结论项分别标记为 adopted、rejected 或 pending，随后批准仅含 adopted 项的结论包。
```

专业角色间的交流不能绕过 Relay。它可以像真人专业间互相追问，但每一次请求与回复都必须带有同一 `trace_id`、轮次和证据引用。

## 6. 结论裁决与 LLM 边界

`case.json` 中的 `decision_ledger` 是下一版“结论裁决台账”的数据源。每条记录包含结论项、来源、状态、总监处理理由和证据引用。

报告 Agent 只能读取 `approved_conclusion_package`，其中仅保留 `adopted` 项。以下内容绝不发送给真实 LLM：完整时间线、已排除推断、待补充材料、人工纠偏前的初步判断，以及任何原始项目材料。

```text
   Relay 仅向受影响的两个专业节点发起第二轮澄清。

6. evidence.submitted x2
   两个专业节点补充对象识别与适用依据。

7. conclusion.proposed
   汇总 Agent 输出事实、证据、冲突状态和建议结论。

8. human.approval
   总监 Human Adapter 批准，或选择退回补充。

9. report.drafted
   报告 Agent 只使用已批准结论包生成 Markdown 草稿。
```

## 7. Demo 要证明什么

- 不同专业节点可以使用不同资料和不同 Agent 实现，但通过同一消息契约协作。
- Relay 控制轮次，避免无休止的 Agent 对话。
- 人能在中途纠正错误前提、收紧核查边界，并对冲突作出可追溯裁决。
- 结论必须关联证据；被排除或待补充的内容不会伪装成最终结论。
- 报告草稿只能在负责人确认后读取已采纳结论包生成。
